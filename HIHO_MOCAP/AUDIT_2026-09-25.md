*The audit agreed on 2026-09-01 and deferred until after the studio test wave. Laptop (`Davids-MacBook-Pro`), read-only.
Three parallel read-only passes (processing and data; capture, calibration and cameras; the Blender side), then the most
important claims checked by hand. No code was changed, nothing was committed, and nothing ran on cameras or in Blender.*

**Baseline:** HEAD `33d6b2d` (1.5.5, committed and installed live) plus the uncommitted 1.5.6 change (voice timing in
`external/record_take.py`, version bump in `__init__.py` and `blender_manifest.toml`; built as `hiho_mocap-1.5.6.zip`,

commits are David's call. Every finding applies to both 1.5.5 and 1.5.6.

**House rule for what comes next:** David reads this, picks fixes one at a time, and each fix gets its own build, zip and
test. Bigger items get a design doc first.

## The short version

- **The normal path works.** When things go right, nothing on Record, Process, Spawn Rig, Bake, Save Out crashes or
  loses a take. The processing pass found no HIGH issues at all.
- **The risks are "when something goes wrong" and "on a machine that isn't David's laptop":** stopping early, cameras that
  run slow together, cameras that come back in a new order, a fresh Mac mini install, a crash in the middle of a run.
- **50 findings: 5 HIGH, 23 MEDIUM, 22 LOW.** Most fixes are small (S).

## Start here: the picks before Art 241 testing (end of October)

Ranked by "would bite a student in the classroom" and "small to fix". Each is one build.

1. **C2 · HIGH · S-M · Carry the "6 of 8 corners" calibration patch to student machines.** (Checked by hand.) David's
   laptop FreeMoCap was hand-edited on 2026-05-09 so a calibration frame counts with 6 of the board's 8 corners. The setup
   scripts install stock `freemocap==1.8.2`, which needs 7 of 8, and the patch is saved nowhere in the repo. The same
   calibration dance will keep far fewer frames on a Mac mini, and the live board badge ("all 6") promises frames the
   solver will throw away.
2. **C3 · HIGH · S · Refuse a take where every camera ran slow.** (Checked by hand: the sidecar writes the *requested*
   fps.) A dim room can halve a C922's frame rate. If all six slow down together, the take passes every check, is labeled
   60 fps, and plays at about double speed.
3. **C1 · HIGH · S (Mac) · A clean stop.** (Checked by hand: the recorder has no signal handling; Blender stops it with
   `terminate()`.) The X next to Record Mocap, or quitting Blender mid-take, kills the recorder before the six videos are
   closed. The folder looks like a normal take, but its videos can't be opened.
4. **B1 · HIGH · S · Save Out FBX should export only the real clip.** (Checked by reading Blender 5.2's own FBX exporter;
   confirm with one test export.) One missing setting makes every tracking dot's movement ride along as its own clip,
   dozens of junk clips per file.
5. **C4 (step 1) · HIGH · S · Record refuses until Show Cameras has confirmed the cameras this session.** Camera numbers
   can shuffle after a reboot or replug, and nothing notices. The solve then uses the wrong camera positions: a garbage
   skeleton with no message pointing at the cameras.
6. **P4 · MEDIUM · S · An RTMPose run must not hang forever if Blender crashes.** (Checked by hand.) Two helper processes
   get stuck holding memory until the computer restarts. Bad on shared lab machines.
7. **P1 · MEDIUM · S · Move the old result aside only after RTMPose proves it can start.** (Checked by hand.) Today a
   failed or cancelled RTMPose run leaves the take with no current result, and the messages don't say where the old one
   went.
8. **C8 + C9 · MEDIUM · S · Messages a student can act on, and the right default env path.** A fresh Mac without camera
   permission says only "no cameras detected", and a student's first error shows David's username (the env preference
   defaults to `/Users/davidbayus/miniforge3/...`).
9. **P7 · MEDIUM · S · Catch iCloud-offloaded videos before processing.** The eval kit had this guard; the port dropped it.
   Offloaded videos make Process look hung for minutes, then fail cryptically.
10. **B3, B4, B5 · MEDIUM · S each · Mode guards.** Save Out fails in Pose Mode; Spawn Rig can overwrite another armature
    that is in Edit Mode; Bake records a T-pose on every frame in Rest Position and still reports success.

**Design first (bigger, each needs a short design doc):** C5 + C6 (dead camera and full disk: a "CAMERA n LOST" banner, a
per-camera live fps meter, which is the old Build B); P3 (keep 2.0's real failure reason); P6 (an interim quality signal
on the RTMPose path); C10 + P15 (Windows); a committed test suite (B11, C17, P16).

## A. Processing and data path (P1 to P18)

The processing pass's answers to the design's promises: **never a silent fallback between trackers: kept. The badge never
says GOOD from the placeholder: kept. The other tracker's results are moved aside, never overwritten: kept** (but see P1,
P2). **Honest failure when a camera worker dies: half kept** (P3). **No double-scramble if upstream fixes the block order:
confirmed**, with one weak spot (P5). Paths with spaces or non-English characters: safe on macOS.

**P1 · MEDIUM · S (reorder), M (restore) · Old results are moved aside before the new run is proven.**
The MediaPipe result is moved aside in the first second, before 2.0 is even imported. If the run fails, is cancelled, or
the 2.0 env is broken, the take has no current result; Spawn Rig and Load Take then give errors that never mention the
aside folder, and a broken env gets "connect to the internet once" advice. `process_take_fmc2.py:561-569` vs `:576-582`;
the MediaPipe twin uses the safe order (`process_take.py:204-216` then `:243-252`). Also: `runner.start()`
(`operators/process.py:159`) isn't wrapped, so a launch error becomes a traceback popup. Fix: move aside after warm
succeeds; word warm failures by cause; on failure or cancel, rename the partial folder and move the earlier result back;
catch OSError around `runner.start()`.

**P2 · MEDIUM · M (S for a refusal) · Loading a moved-aside result silently loads the current one.**
Picking `output_data_mediapipe_<time>/` in Load Take shows the take's *current* result, labeled as the take, with no
warning; if the current result is missing, it throws a traceback. Both results also build a rig with the same name, so
loading the second deletes the first. `operators/load_take.py:47-65`, `operators/spawn_rig.py:37-42`, `core/loader.py:119`.
Fix: pass the chosen folder through to Spawn Rig and the loader, or refuse `output_data_*` folders with restore
instructions; put the tracker name in the rig name.

**P3 · MEDIUM · S-M · When 2.0 fails the normal quiet way, the reason is lost.**
2.0 usually fails with exit code 0; the panel then always says "it stopped without writing a new RTMPose result", and the
real reason (which camera, what broke) is logged once and thrown away. A leftover `FMC2_RUN_INFO.json` from an older run
can also supply an old error, and multi-line errors reach the panel as their first line only. `process_take_fmc2.py:601-611`,
`:304-321`, `:542-543`; `core/external_runner.py:333-347`. 2.0 publishes the cause as a FAILED progress message, readable
through `manager.get_progress_updates()`. Fix: copy FAILED details into the error record; save the run output to
`FMC2_RUN_LOG.txt` in the take folder; delete old run info at start; collapse multi-line errors.

**P4 · MEDIUM · S · A Blender crash or Force Quit leaves two processes hung forever.** (Checked by hand.)
Once Blender is gone, the pass-through thread dies on its first print, nobody empties the run stage's output pipe, and
every logging thread in 2.0 blocks, including our heartbeat loop, so neither the 4-hour limit nor 2.0's own watchdog can
fire. They hold RTMPose's memory until restart. `process_take_fmc2.py:195-207`. The agent confirmed the mechanism with a
stand-alone copy of the pattern. A normal Quit is clean. Fix: in `_pump`, catch the write error, stop echoing, keep
draining; guard `_emit` the same way.

**P5 · MEDIUM (possible) · S · The un-scramble check reads "no evidence" as "not scrambled".** (Checked by hand.)
If one hand or the face is never tracked for a whole take (a hand in a pocket, a mask or costume head), the un-scramble
switches itself off although alpha.23's files *are* scrambled: the hands come out built from face points, the panel says
"complete". `process_take_fmc2.py:387-403`. How often depends on whether 2.0 writes all-empty columns for unseen points
(unconfirmed). Fix: treat missing data as unknown and fall back to the pinned version's known order; before the wrist
attach, check each hand root sits within about 150 mm of its body wrist (catches any future mis-order too); report the
decision in `PROCESS_QUALITY.txt`.

**P6 · MEDIUM · S-M · The default tracker can't warn about a bumped camera or the wrong calibration.**
On RTMPose the only quality line is the share of frames with shoulders and hips found, which stays at 100 % with a bad
calibration, and 3 % gets the same neutral icon as 100 %. The MediaPipe badge was the only automatic alarm (it caught
bumped cameras at 27.7 and 58.3 px). `process_take_fmc2.py:632-645`; `ui/panels.py:169-170`. Fix (interim): add the bone
wobble number the take log already uses, with a CHECK band; a tracked-share floor (under about 80 % says CHECK, under
about 5 % fails); look at 2.0's `per_camera_weights.npy` for a consistently down-weighted camera.

**P7 · MEDIUM · S · No guard for iCloud-offloaded videos.**
The eval kit's `fmc2_take.sh` re-downloaded offloaded videos; the addon port dropped it. Process then looks hung and ends
in "Stream timeout" or "moov atom not found". New machines default "Save to" to `~/Desktop` (`properties.py:283-291`).
`process_take_fmc2.py:94-113`, `process_take.py:150-166`. Fix: before warm, flag any `Camera_*.mp4` with full size but no
disk blocks; `brctl download` and wait, or stop with "Camera_3 is still in iCloud. In Finder, right-click the take folder
and choose Download Now."

**P8 · MEDIUM · S-M · No pre-check against the calibration; one camera silently goes flat.**
A camera the calibration doesn't know fails only after the full detection pass, with P3's generic sentence. With exactly
one camera video, 2.0 quietly switches to a flat "planar projection" fallback and reports success, and Spawn Rig builds a
flat fake-3D rig. `process_take_fmc2.py:556-559, 571-573`; 2.0 `posthoc_mocap_task.py:78-79`, `triangulator.py:100-116`.
Fix: refuse fewer than 2 videos; read camera names from the calibration TOML and refuse unknown ones; stop with the
recorder's own sentence if `RECORDING_REPORT.txt` says MISMATCH.

**P9 · MEDIUM · S · A stuck run takes 4 hours to be called a failure.**
Default timeout 4 hours against a measured pace of about 5 s per second of take; the warm stage has no limit; on a full
disk the end of the run stage can skip its hard exit and hang; freshness checks only the body file.
`process_take_fmc2.py:507, 309-310, 206, 335-342, 596-600`. Fix: timeout about 120 s + 20 x take length; limit the warm
stage; make the hard exit always run; check freshness of all four files the shim reads.

**P10 · MEDIUM · S · Moved takes (08-04 #6, still open, new symptom).**
A moved or copied take keeps absolute links to the old place: RTMPose says "no camera videos could be opened" while the
videos sit in the folder; partly broken links process with fewer cameras and nobody is told; on exFAT every video is
silently copied. `process_take_fmc2.py:99-113, 557-559`; `process_take.py:150-166`. Fix: relative links, remake broken
ones, say so when falling back to copying.

**P11 · LOW · S · Progress notes never reach the student.** "Earlier results moved aside to ...", "warming the RTMPose
model", the camera count: Blender ignores info lines and the RTMPose status is a bare clock. `core/external_runner.py:343-367`,
`operators/process.py:89-94`. Fix: show the latest info line under the clock; name the aside folder in the finish message.

**P12 · LOW · S · The stamp doesn't say which calibration was used.** With a blank Calib box both trackers use FreeMoCap's
undated `last_successful_calibration.toml`. `process_take_fmc2.py:657-668`, `process_take.py:294-301`. Fix: stamp the
calibration's name, modified time and a short fingerprint.

**P13 · LOW (possible) · S · Record stays clickable while Process runs.** Same as C7.

**P14 · LOW · S · Motion keyed from the scene's start frame, then start forced to 1.** Same as B6.
`core/virtual_landmarks.py:94-95`, `core/output_rig.py:143-144`, `core/scene_clock.py:38-44`.

**P15 · LOW (Windows, later) · M.** Cancel and Quit stop only the outer helper; links need Developer Mode so videos are
copied; the two scripts write status files in different encodings. `core/external_runner.py:313-319, 211`;
`process_take_fmc2.py:188-192, 107-110`; `process_take.py:115`.

**P16 · LOW · M · No committed tests for the RTMPose script; the twin scripts are drifting.** The 1.5.1 "30 checks"
aren't in the repo. The two processing scripts duplicate tracker detection, move-aside, status files and the file list,
and already differ. A standard-library-only `external/hiho_protocol.py` would import in both envs.

**P17 · LOW · S · Map the Volume fails on RTMPose takes.** Same as C16. `external/volume_map.py:99-107`.

**P18 · LOW · S · Out-of-date comments.** `core/enforce_rigid_bodies.py:23-25`, `properties.py:182`,
`core/external_runner.py:1-8, 57`, `operators/__init__.py:17`.

## B. Capture, calibration and cameras (C1 to C17)

Retired files (`operators/record.py`, `operators/cameras.py`, `operators/capture_cameras.py`, `core/capture_cameras.py`,
`core/blender_preview.py`) are imported by nothing and not in the zip: no findings there. The 1.5.6 voice change adds no
crash path (two phrases can overlap if the length guess is short; cosmetic).

**C1 · HIGH · S (Mac signal route), M (cross-platform stop file) · Stopping from Blender, or quitting Blender mid-take,
destroys the take.** (Checked by hand.)
The X next to Record Mocap (hover text "Closes the camera window") sends SIGTERM; the recorder has no handler, so the
video writers are never released. The student sees "Capture window closed." and the broken folder looks like any other
take. Quitting Blender does the same through `unregister()`. `operators/external_capture.py:124, 215-232`;
`core/external_runner.py:313-319`; `operators/__init__.py:118-120`; `__init__.py:173-174`. Possible extra: if the
recording window opens behind Blender, ESC never reaches it and the X is the only stop a student finds. Fix: a clean-stop
request routed to the existing ESC path (SIGTERM handler on Mac; a STOP file also works on Windows), and shutdown waits a
few seconds for the recorder to finish.

**C2 · HIGH · S-M · Student machines calibrate with a stricter rule than the laptop.** (Checked by hand.) See the picks.
Fix: commit the patch; both setup scripts apply and verify it; `calibrate.py` reads the installed line at `--check` and at
Solve and refuses in plain words if it still says 7. (Backlog #7, "save the anipose patch", was never done.)

**C3 · HIGH · S · If every camera runs slow together, the take is accepted as 60 fps.** (Checked by hand.)
All six at about 30 fps: the take stops at the clock, counts even up, the mismatch check passes, the sidecar says 60, and
FreeMoCap's filter and the Blender scene clock both run at 60. The recorder's own "short take" verdict is an INFO line
Blender ignores. `record_take.py:633-635, 657-660, 185-187, 670, 679-691`; `camera_manager.py:310-318`. Fix: on every
stop, compute the real rate; if more than about 5 % low, fail in plain words ("The cameras only managed about 30 frames a
second, so this take would play too fast. Turn up the lights or close other apps."). At minimum, write the measured rate
into the sidecar and show the verdict.

**C4 · HIGH · S (step 1), M (steps 2-3) · Nothing notices a camera order or rotation change since calibration.**
Rotations are keyed by camera number and never saved per take; Record trusts the Cameras box saved in the .blend.
`record_take.py:56-62, 679-685`; `external_capture.py:190-201`. Fix: (1) refuse Record unless Show Cameras confirmed the
box this Blender session (a reboot always means a Blender restart); (2) put rotations in every sidecar and compare take
against calibration at Process; (3) refuse a camera list or portrait/landscape flip the calibration file doesn't match.

**C5 · MEDIUM · S-M · A take whose videos never reached the disk can be reported as recorded.**
The frame count goes up whether or not the write worked, and the result of `start_writing(...)` is thrown away. Disk full
mid-take: unplayable files, "Take recorded." No writer can open: 0 frames, the voice says "recording" then "done", still
reported as recorded. `camera_manager.py:135-137, 163-164, 287`; `record_take.py:177-187, 196-200`. Fix: after stopping,
open each video and check it decodes with the counted frames; check free space before recording; treat a failed
`start_writing` as an error at the start.

**C6 · MEDIUM · M · A camera that dies mid-take isn't noticed until the end, and its frozen picture keeps "reading" the
board.** The badge and voice keep counting the frozen frame; a 120 s dance runs to the end before failing. In Show
Cameras, a camera that opens but sends nothing is an unlabeled black square. `camera_manager.py:111-114, 143-147`;
`record_take.py:279-290, 376-379`. Fix: watch each camera's last-frame time; after about 1 s show and say "CAMERA n LOST",
stop early; show live fps per tile in Show Cameras (Build B, which would have caught the 08-01, 08-22 and 09-05 slow
cameras).

**C7 · MEDIUM · S · Record is allowed while Process or Solve is running.** RTMPose runs six trackers at once, so recording
take 2 while take 1 processes may drop frames (not measured). `external_capture.py:179-181`; `calibration.py:110-112,
198-201`; `process.py:109-114`. Fix: grey out in both directions with hover text saying why.

**C8 · MEDIUM · S · "No camera" and permission failures give messages a student can't act on.** Missing camera permission,
a hub switched off, or a stale Cameras box all end as "no cameras detected"; OpenCV's "not authorized" line is lost; one
hub off shows "4 of 4"; stuck cameras are waited on one by one, up to 10 s each. `record_take.py:544-546, 562-567`;
`external_runner.py:332-338`; `camera_manager.py:251-252`. Fix: plain next steps (hubs on, close other camera apps, System
Settings > Privacy & Security > Camera, run Show Cameras again); attach OpenCV's line; warn when fewer cameras are found
than the ring has; one overall 10 s deadline.

**C9 · MEDIUM · S (defaults, text), M (installer) · Gaps in the student install path.** The env preference defaults to
David's miniforge path (`properties.py:266`), not the setup's `~/freemocap-env`; setup installs only the MediaPipe env
while RTMPose is the default (the 2.0 installer is already owed); neither setup script mentions camera permission.

**C10 · MEDIUM · M · Windows (untested).** `say` failures are swallowed, so a solo performer gets no countdown or count;
only a Mac camera fallback exists (Windows should try DirectShow first); `terminate()` is a hard kill; `os.killpg` doesn't
exist, so Cancel leaves FreeMoCap children running; OneDrive-synced Desktops and accented usernames are possible traps.
`record_take.py:115-127`; `camera_manager.py:47-58`; `external_runner.py:313-319`.

**C11 · MEDIUM · M · Camera timing is never measured.** Writers open one after another (the first camera may lead by a
frame or two for the whole take); no per-frame timestamps; elapsed time uses the wall clock. The stale "FreeMoCap
synchronizes in post" comment is still at `camera_manager.py:281-282`. Fix: save per-frame capture times per camera; open
all writers, then start together; `time.monotonic`.

**C12 · LOW · S · The sidecar is written last and leaves out what later steps need.** If Blender crashes mid-take, the
orphaned recorder dies at its first print, before the sidecar exists, and the MediaPipe path then treats the 60 fps take
as 30. An ESC-stopped take claims the full length. `record_take.py:670, 679-691`. Fix: write the sidecar at start, update
it at the end, guard `_emit` against a closed pipe.

**C13 · LOW · S · The voice says "done" even when the take failed.** `record_take.py:665` runs before the check at
`:671-675`. Fix: say "recording failed, check the screen".

**C14 · LOW · S · Launchers wired to David's machine ship in every zip.** Same as B10. `HIHO_Record.command:18-19` (also
still guesses cameras 0-5 and wrongly says nothing was saved after a mismatch), `HIHO_Camera_Preview.command:8-9`,
`diagnostics/HIHO_Camera_Speed_Probe.command:3-4`.

**C15 · LOW · S · The rotations file can silently reset.** A corrupt `camera_rotations.json` makes every camera record
unrotated, with no message. `record_take.py:56-71`. Fix: temp file plus `os.replace`, and a visible warning on read
failure.

**C16 · LOW · S-M · Map the Volume hasn't caught up with RTMPose.** It needs a MediaPipe center-of-mass file the RTMPose
converter doesn't write, and its reprojection column would read a placeholder 0.00 px. Studio panel only.

**C17 · LOW · M (tests), S (rest) · Maintainability.** No committed tests for the clock stop, report verdicts, countdown,
`_Voice` or the board reader; `record_take.main()` is about 200 lines; dead code (`calibration.py:9`, `:94-95`,
`record_take.py:271`); `_redraw_panels` copied in 3 files, the env check in 4. Best value: C1, C3, C5, C12 and C13 all live
in the last ~60 lines of `record_take.main()`, so design them together and ship them one build each.

## C. The Blender side (B1 to B15)

Nothing here imports the vendored ajc27 code at runtime (`core/foot_locking.py` is our own port). All 33 files parse.

**B1 · HIGH · S · Save Out FBX exports every tracking dot as its own animation clip.** (Checked by reading the exporter.)
The student's FBX holds the real take plus dozens of junk clips, each sliding the frozen rig around like one dot; a game
engine lists them all, and the export is probably much slower (not timed). `operators/save_out.py:81-85`. GLB is smaller
in scope (it only picks up leftover baked actions, see B2). Fix: pass `bake_anim_use_all_actions=False,
bake_anim_use_nla_strips=False`, which writes one clip of exactly what plays on the timeline, whether the animation is on
the rig or pushed to NLA. Confirm first: re-import any exported FBX into an empty scene and count the actions.

**B2 · MEDIUM · S-M · Spawn Rig silently throws away this take's finished rig.** Clicking Spawn Rig again after Bake (or
after the NLA push) deletes the baked rig, hand-cleaned keys included, with no question; the orphaned action vanishes on
save and reopen, and exports as a stale clip until then. If the reload fails, nothing replaces it. `spawn_rig.py:51,
109-132`; the addon itself tells students to re-spawn (`lock_feet.py:251`). Fix: if the rig is baked or has NLA strips,
ask first or rename it aside; delete only `hiho_*` children.

**B3 · MEDIUM · S · Save Out fails with a Python error in Pose Mode.** `bpy.ops.object.select_all` runs before the `try`
(`save_out.py:73`) and refuses outside Object Mode. Same pattern at `spawn_test_face.py:33` and `output.py:46`. Fix: switch
to Object Mode first, as Load Take does (`load_take.py:74-75`).

**B4 · MEDIUM (possible, destructive) · S · Spawn Rig can overwrite another armature that is in Edit Mode.** With an
armature already in Edit Mode, `armature_add` adds a bone to it instead of creating a new object, and Spawn Rig then
renames it and deletes all its bones. `build_rig.py:217-226`; no mode check in `spawn_rig.py` (Auto-Rig has one,
`autorig.py:56-57`). Confirm in a scratch file. Fix: exit to Object Mode at the top of Spawn Rig.

**B5 · MEDIUM · S · Bake can record a T-pose on every frame and still report success.** In Rest Position the bake samples
the bind pose, removes the constraints, and Save Out then exports a T-pose file. `bake_animation.py:119-131`. Fix: refuse
in plain words when `pose_position == 'REST'` or in Edit Mode; optionally refuse if the pelvis never moved.

**B6 · MEDIUM (edge) · S · The take lands off the timeline when the file doesn't start at frame 1.** Keys start at the
scene's start frame, then `spawn_rig.py:100` resets start to 1; a file that starts at 1001 bakes a frozen pose.
`output_rig.py:143`, `virtual_landmarks.py:94`, `scene_clock.py:40`. Fix: set the scene clock before keying, or always
key from frame 1.

**B7 · MEDIUM (edge) · S · Add Camera Videos rejects relative and `~` paths, and stacks planes on every click.**

## Strengths worth keeping (a future refactor must not break these)

1. **Never a silent fallback between trackers;** refusals stay in the status line (`process.py:116-122, 139-142`).
2. **Move, never delete,** in both directions; the tracker stamp travels inside `output_data/`.
3. **The freshness check** (`process_take_fmc2.py:591-611`): essential, because 2.0 exits 0 on failure and never clears
   `output_data/`.
4. **The proven 2.0 workarounds:** heartbeat refreshed by hand (never `start_heartbeat()`), model warmed in one process,
   hard exit only after files are on disk, fps from the sidecar, and a double-scramble guard that switches itself off.
5. **The slow-camera case handled end to end:** stop at the clock, even up counts with a timeout that exposes a dead
   camera, RECORDING_REPORT.txt names the camera and its fps; disk-verified tests in `test_equalize_stop.py`.
6. **A blank Cameras box is refused, never guessed;** excluded cameras stay visible so they can be switched back on.
7. **The voice can never break a recording** (strictly best-effort).
8. **Correct Blender 5.x keyframe writing** (slot, layer, strip, channelbag, bulk `foreach_set`) and **no stale-data
   risk:** shared state holds no Blender data; register and unregister match; no handlers; timers stop themselves.
9. **A sound bake:** sample first, then key; remove only HIHO_ constraints; a pose-neutral continuity pass.
10. **Safe process and path handling:** arguments passed as lists everywhere, atomic status files, the whole process group
    killed on Cancel and on Quit, crash text kept.
