# HIHO MOCAP Code Audit — 2026-06-09

**Audited:** v1.3.8 source at `SOFTWARE/HIHO_MOCAP/` (the canonical build) plus the shipped `hiho_mocap-1.3.8.zip`.
**Scope:** HIHO's own code (~4,700 lines: `core/`, `operators/`, `external/`, `ui/`, `panel/`, shell). `vendor/` (bundled FreeMoCap/ajc27) deliberately excluded — it's upstream code we keep 1:1.
**Method:** four parallel review passes (capture path, processing/calibration, rig building, addon shell), already-known issues filtered out, then the serious findings re-verified by direct code reading. Findings marked **[verified]** were confirmed line-by-line in a second pass; others are reviewer findings with quoted code, marked with confidence.
**No code was changed during the audit itself.** This is a findings document. Fixes go through the normal design → one-change-at-a-time → test process.

Each shipped as its own zip with headless tests — see `SESSION_HANDOFF_2026-06-09.md`. **Still open:** M2, M3, M6, M8, M9, M10, M14, M15, M19 and most LOW items below.

**Relationship to other docs:** complements `BUGS_AND_BACKLOG.md` (which tracks FreeMoCap-layer friction from real sessions — still accurate). This doc covers the addon's own code. Known open items (wrist flip, plane auto-roll collision, 30 fps bake-in, finger noise) are NOT re-listed here.

---

## The headline

The pipeline is in good shape **when everything goes right** — the 6/7 clean BASEMENT run is real, and several scary areas (Blender 5.2 API compliance, rotation math, the L/R landmark mapping) checked out completely clean.

The dominant problem is one family: **when something goes wrong, the addon doesn't notice, and often actively reports success.** Most serious findings below are variations of "a normal classroom event produces a silent failure or a false success message." For a tool whose users are students and a non-programmer, silent failure is the worst failure.

## SERIOUS — will bite at the rig or in class

### S1. Two takes in one scene → second skeleton is frozen in T-pose, with a false "63 bones bound" success message **[verified]**
`core/bind_to_rig.py:180-182, 195, 200-207` + `core/virtual_landmarks.py:30-31`

Blender object names are globally unique. The first take's empties are named `hiho_right_wrist` etc.; spawn a second take in the same scene and Blender auto-renames its empties `hiho_right_wrist.001`. The empty-lookup table keys on the exact post-prefix name (`right_wrist.001`), but the constraint code looks up the exact original name (`right_wrist`), finds nothing, and **silently skips every constraint** (`if target_obj is None: continue`). The bone is then appended to the "bound" list anyway (line 195 sits outside the constraint loop), so the operator reports full success. Result: take B's skeleton stands frozen while its empties animate. Comparing two takes side-by-side is a completely normal classroom workflow. Same root cause makes `ensure_virtual_empties` re-create 6 keyframed empties on every click for take B.

**Fix direction:** strip Blender's `.001`-style numeric suffix when building the index in `_index_skelly_empties`, and only count a bone as bound if at least one constraint was created. (The code comment says "substring-matched ... same approach as ajc27" — the port lost the tolerance; the lookup is exact-match.)

### S2. Cancel doesn't cancel — FreeMoCap keeps running invisibly and the addon locks up until Blender restarts **[verified]**
`core/external_runner.py:141-143` (stop), `79-86` (is_done), `operators/process.py`, `operators/__init__.py`

`stop()` calls `terminate()` on the parent helper script only. FreeMoCap's multiprocessing children are separate processes: they survive, keep burning CPU on detection, and hold the stdout pipe open. Meanwhile every "done" signal originates in the parent that was just killed (it writes the DONE/ERROR sentinel files), so `is_done` never flips: the poll timer spins forever, `STATE["processor"]` is never cleared, and Process/Solve/Cancel stay greyed out for the rest of the Blender session. Quitting Blender mid-process has the same gap (`shutdown()` uses the same `stop()`), leaving headless FreeMoCap workers running on the machine.

**Fix direction:** launch with `start_new_session=True` and kill the whole process group in `stop()`; have `stop()` itself set the error/done state so the poll closes out.

### S3. After a Blender restart, Solve Calibration is dead with no recovery — its picker exists but is never drawn **[verified]**
`properties.py:69-74` (the property, with `DIR_PATH` picker subtype and a description promising "you can also pick an older board take"), `ui/panels.py:45-53` (Calibrate section draws only buttons), `operators/calibration.py` (Solve's poll requires `calibration_take_path`)

`calibration_take_path` is set when you record a calibration, lives in the unsaved scene, and dies with a Blender restart. The Solve button then greys out, and because **no panel draws the property**, there is no way in the UI to point it at the board take sitting on disk. Only recoveries: re-record a calibration (needs the rig) or the Python console. This is precisely the failure pattern that produced the project's own picker rule ("auto-populate dies on Blender restart; picker survives") — the property was even built for it, then never wired into the panel.

**Fix direction:** one `layout.prop(scene_settings, "calibration_take_path")` line in the Calibrate section.

### S4. Same disease, second button: Spawn Rig is dead after restart — `last_processed_path` is label-only **[verified]**
`properties.py:33-37` (no picker subtype), `ui/panels.py:79-83` (drawn as a read-only label), `operators/spawn_rig.py` + `operators/output.py` (polls require it)

`last_processed_path` is only ever written by the processing-complete callback. After a restart/new file it's blank, both Output buttons grey out, and the only in-UI recovery is to **re-run Process Mocap on the whole take** (minutes of compute) to repopulate a string. A student who processed yesterday and opens a fresh file today cannot spawn their rig.

**Fix direction:** give the property `subtype='FILE_PATH'` and draw it as an editable prop, or derive a fallback from `last_take_path` (`<take>/output_data/...npy`) in the polls.

### S5. Stopping a recording early (ESC) produces a take FreeMoCap will reject — and you can't abort during the countdown
`core/camera_manager.py:278-284`, `external/record_take.py:239, 246-251` — reviewer finding, high confidence (mechanism verified via quoted code + the documented FreeMoCap frame-parity constraint, `BUGS_AND_BACKLOG.md` #5)

The equal-frame-count guarantee only holds on the auto-stop path. `stop_recording()` stops each camera's writer thread at whatever count it happens to have reached; at any arbitrary instant the four counts almost never match, and FreeMoCap rejects videos that differ by even one frame. The take *looks* recorded; it fails minutes later at Process with a cryptic error, performance unrecoverable. The UI advertises ESC-to-stop, so this is a normal action. Bonus wrinkle: during the countdown the key events are discarded, so ESC does nothing until recording has already started — the only way out of an accidental Record is to wait, then ESC, producing exactly this broken take.

**Fix direction:** after early stop, trim all cameras to the minimum frame count before finalizing; honor ESC during countdown.

### S6. The capture buttons are fire-and-forget — every launch failure is silent **[verified pattern; found independently by two reviewers]**
`operators/external_capture.py` (~51, 73-81), `operators/calibration.py` (~104-114)

The external recorder script carefully emits `HIHO_ERROR::` / `HIHO_DONE::` marker lines — its own docstring says they're "marker lines Blender keys on" — but **none of the three operators that launch it ever read them.** They `Popen(cmd)` with inherited stdout (invisible for a Dock-launched Blender), set the take path optimistically before a single frame exists, and report success. Concrete silent triggers: a typo in the Cameras field (ValueError before any window opens), cameras busy or macOS camera-permission denied for the conda python, a broken env. The student experience is "I clicked Record and nothing happened." There is also no guard against double-clicking Record (two recorders contending for the same cameras) and no way to stop a recorder from Blender. This is the sharpest contrast in the codebase: the processing path got the full runner + sentinel treatment; the capture path — the one students touch first — got none.

**Fix direction:** hold the Popen handle in STATE (enables a double-click guard and a Stop), poll it briefly for early exit and surface stderr; gate Solve on the recorder's own completion sentinel.

## MEDIUM — real, conditional, mostly the same "silent" family

### Processing & state lifecycle

- **M1. Stale sentinel race on re-processing [verified mechanism; found independently by two reviewers].** `core/external_runner.py:79-86, 108-139` + `external/process_take.py`. Sentinel files from a previous run of the same folder are deleted by the *child* (after conda Python's slow startup), but Blender's first poll fires at 0.5 s and `is_done` trusts any sentinel it sees. Re-running a take (routine: re-solve with better calibration) can instantly report yesterday's result while the new run continues unsupervised and rewrites `output_data/` underneath whatever you do next. **Fix: `start()` should delete both sentinels parent-side before `Popen` — one structural line, kills the whole class.**
- **M2. The panel-recommended default calibration defeats the 1.3.8 multi-path search.** `external/score_calibration.py:61-79`. The reverse-derivation assumes stamp-named tomls (`<stamp>_camera_calibration.toml`); the fallback `last_successful_calibration.toml` doesn't match the pattern, so after a restart with blank paths, Check Calibration fails with "charuco 2D data not found" in exactly the configuration the panel recommends ("Calib blank = use last_successful..."). The 6/7 live success worked because in-session paths were still populated.
- **M3. Scorer failures are swallowed.** `core/calibration_quality.py:29-52`: stderr is captured then discarded, return code unchecked, and the fallback error tells the user to "see system console" — where, because of `capture_output=True`, nothing was printed. The scorer script itself has no try/except and a latent IndexError (`board[valid]` when point counts mismatch, right after a warning about exactly that).
- **M4. Loading another .blend mid-run kills the poll timers.** `bpy.app.timers.register` defaults to non-persistent; a student opening their character file during a long solve orphans `STATE["processor"]` — completion is never reported and the buttons stay dead until restart. Fix: `persistent=True` or a load-post handler.
- **M5. Blender-relative (`//`) and `~` paths are never normalized.** No `bpy.path.abspath` anywhere in the addon. With a saved .blend and Blender's default relative-path preference, the file browser stores `//../...`, and every `os.path.isdir` gate rejects the path the user just picked. This quietly undermines the picker-recovery design (S3/S4).

### Capture provenance & robustness

- **M6. Rotations are keyed by bare camera index.** `~/.hiho_mocap/camera_rotations.json` is `{index: degrees}`; USB enumeration order is unstable across reboots, and nothing binds an index to a physical device or warns on staleness. A shuffle silently mis-rotates recordings AND invalidates the calibration extrinsics the same way. The only defense is the human "Show Cameras first" ritual. Cheap mitigation: write the rotations used (plus date) into each take folder so a bad take is at least diagnosable.
- **M7. A camera dying mid-take = recording never ends.** Read failures retry forever in a tight loop, `is_recording` only flips when ALL writers hit target, there's no wall-clock failsafe, and `start_writing`'s return value is discarded so a writer that failed to open (disk full) silently records zero frames. ESC out of the hang then triggers S5.
- **M8. Recorded fps is the requested fps, never measured.** C922s halve their frame rate in dim light; frame-count-bounded recording then delivers 1800 frames over ~120 real seconds, stamped 30 fps → the baked skeleton moves at double speed, no error anywhere. The data to detect this (elapsed time vs frame count) already exists.
- **M9. Equal frame count is treated as synchronization.** `process_take.py` just symlinks files into `synchronized_videos/` — nothing actually synchronizes, and a comment claims FreeMoCap does ("FreeMoCap synchronizes in post"). Dropped frames shift one camera's timeline while keeping final counts equal; with no per-frame timestamps recorded, drift is undetectable after the fact. Symptom: mushy triangulation on fast motion despite an "excellent" calibration badge.
- **M10. `camera_rotations.json` IO swallows everything.** Corrupt file → every camera silently records unrotated (sideways performers, garbage tracking, discovered after processing). Saves are non-atomic (unlike the sentinel writer in the same codebase) and save failures pass silently.

### Rig building & data

- **M11. NaN alignment fallback → invisible rig with a success message [two reviewers converged].** `core/loader.py:286-287, 295-326`. When no frame passes the four-feet-tracked filter (seated takes, chest-up framing, feet occluded), alignment falls back to frame 0 with no finiteness check; all-NaN feet there poison every landmark on every frame via `nanmean` → cross products → matrix multiply. Nothing downstream validates: the student is told "Built rig... Press Spacebar" over an empty viewport. Fix: one `np.isfinite` check with a plain-English error ("couldn't find a still, fully-visible standing moment — start takes with 5 seconds standing in view").
- **M12. NaN keyframes for never-tracked limbs.** `core/output_rig.py:144-147`, `core/virtual_landmarks.py:80-83`. Everything else filters NaNs (bone-length math, enforce) but the keyframe writers don't; a hand that stayed off-camera the whole take writes NaN keys, DAMPED_TRACK normalizes a NaN vector, and the hand chain explodes/vanishes — inherited by any later bake.
- **M13. Takes missing hand/raw_data files crash Spawn Rig with a raw FileNotFoundError [two reviewers converged].** The processing script declares success on the body npy alone; the loader hard-requires both hand npys plus the reprojection-error npy. Legacy takes (5.0-era monolith), body-only tracker settings, or a partially-copied `output_data/` die at Spawn with a cryptic error far from the cause. Either degrade to body-only gracefully or validate the full file set at processing time.
- **M14. One Spawn Rig click runs the full load+enforce pipeline three times.** `operators/spawn_rig.py:52, 58, 64` each call `load_aligned_data` (spawn empties / virtual empties / bone-lengths), and enforce is per-frame Python recursion over 63 bones — tens of seconds of frozen UI on multi-minute takes, tripled. Load once, pass the dict; vectorize enforce later.
- **M15. Spawn Empties and Add Camera Videos duplicate data on every click.** No purge (unlike Spawn Rig, whose purge is clean) — repeated clicks stack identical planes and add 75 empties + 75 actions with `.001` suffixes, which also arms S1 for that take.

### Shell & packaging

- **M16. `register()` still runs the dissolved bundled-FreeMoCap/ajc27 machinery.** `__init__.py:75-137`. The shipped zip contains neither `vendor/` nor wheels (correct, by design), so every launch prints two scary, *expected* warnings ("bundled FreeMoCap failed to import", "bundled ajc27 missing") that will misdirect any future debugging session. The dev-only branch also self-installs ajc27 as a second addon via `bpy.ops` inside `register()` and never undoes it on unregister — an Extensions-compliance landmine if ever reactivated. The headless pivot made all of it legacy; `core/` has no runtime ajc27 imports.
- **M17. `bl_info` says version (1, 2, 0); the manifest says 1.3.8.** Legacy installs and anyone reading the source get the wrong version by six releases.
- **M18. The FreeMoCap env path is machine-level config stored per-Scene.** `properties.py:47-58`, defaulting to `/Users/davidbayus/...`. Scene props reset in every new .blend — on a student machine every fresh file silently points at David's path until re-picked. Belongs in AddonPreferences (survives restarts and new files); the addon currently has no preferences class. The TODO in source acknowledges the default; the storage tier is the deeper issue. **This is the single biggest blocker between 1.3.8 and any student install.**
- **M19. Calibration board geometry is hardcoded in three places.** `"5x3"` / `100 mm` in `operators/calibration.py:169`, `external/calibrate.py:76-77`, `external/score_calibration.py:98-100`. A student with a differently-printed board doesn't get an error — a wrong square size uniformly rescales the world, producing a wrong-sized skeleton with an "excellent" reprojection score. Deserves a panel field more than the path defaults do.

## LOW / design debt

- **L1. The dead pre-headless capture stack is unmarked and diverges dangerously.** `operators/record.py`, `operators/cameras.py`, `operators/bind.py`, `core/blender_preview.py`, `core/freemocap_runner.py`, plus the deliberately-kept `capture_cameras.py` pair. All verified unregistered/unreachable (good), but they look canonical, ship in the zip, and contain traps: `cameras.py` builds a CameraManager with **no rotations** (bypasses the 1.3.7 system), `bind.py`'s poll references a property that no longer exists (`settings.target_rig` — instant AttributeError-per-redraw if ever re-wired), `freemocap_runner.py` carries a drifted STAGES table and docstrings elsewhere still point at it as live. Per the never-delete rule: add a loud `RETIRED — not registered; live path is X` header to each, and exclude them from the build.
- **L2. Doc-rot cluster.** `ui/panels.py` docstring describes camera-live gating that no longer exists; `core/output_rig.py` docstring says "33 empties... armature lands in v1.1" (it's 75, and the armature shipped); `operators/output.py` says "Spawn Rig" but is Spawn Empties; `operators/bind.py` claims Rigify-metarig names while the table is ajc27 names; `operators/process.py` says it kicks a FreeMocapRunner. For a project whose code doubles as curriculum, these actively mislead.
- **L3. Five bone/landmark name tables must stay in sync by hand** (`_ARMATURE_DEFINITION`, `_TPOSE`, `BONE_HEAD_TAIL_MAP`, `_CONSTRAINTS`, `LANDMARK_HIERARCHY`). Cross-checked: they agree today. Nothing enforces it; a cheap import-time assertion would turn silent drift into a loud error.
- **L4. Marker strings, default-toml paths, output roots, and npy filenames are duplicated across the Blender/external boundary** (5 files). Some duplication is forced (different interpreters), but a single constants module under `external/` would shrink the sync surface. The fragile chain to watch: timestamp folder name → FreeMoCap's toml naming convention → the scorer's reverse-derivation (M2 is the first crack).
- **L5. `frame_end` math assumes `frame_start == 1`** (`core/output_rig.py:100` vs `:138-139`) — off-by-N with custom start frames; should be `start_frame + num_frames - 1`.
- **L6. `bpy.ops` operator calls inside core modules.** `build_freemocap_armature` dies if the user is in Edit/Pose mode on another object (poll failure mid-spawn, after empties were already rebuilt — confusing half-state). Mode-guard or build via `bpy.data`.
- **L7. Check Calibration blocks the UI thread** (up to the 120 s timeout) — deliberate and documented, but a stuck env looks like a crashed Blender.
- **L8. Calibration recordings land on the iCloud-synced Desktop** (`~/Desktop/HIHO_CALIBRATIONS`) — "Optimize Mac Storage" can evict the local copies; relevant to the long-term-archive checklist.
- **L9. Small leaks/raciness:** progress cursor never closed if the addon is disabled mid-process; completion callbacks write results to whatever scene is current (multi-scene files); latent `TypeError` in `ExternalProcessRunner` if a future caller passes `calibration_toml=None` on the default-args path (both current callers guard it).
- **L10. Cosmetics:** "Show Science Mode" toggle is fully inert (and promises ajc27 panels that shipped builds never install); `bl_order = 0` on the Studio panel doesn't actually order it (tie with main panel falls back to registration order); `Camera_10` will sort before `Camera_2` lexicographically when camera scaling lands (July); `.command` launchers + `vendor_patches/README.md` ship in the zip; manifest maintainer email is a placeholder (TODO'd).

## VERIFIED CLEAN — checked explicitly, no findings

- **Blender 5.2 Slotted Actions compliance:** zero uses of removed `action.fcurves`; both keyframe writers use the correct slots → layers → strips → channelbag recipe. The addon is 5.2-safe on this axis.
- **No `pose_bone.matrix` scale-bug exposure** (no pose-matrix assignment anywhere; rig is constraint-driven, built via edit bones).
- **L/R landmark mapping is correct:** uniformly direct, matching ajc27 — the upper-mirror/lower-direct rule applies to single-cam image-space (PPParty V2), not FreeMoCap's world-space triangulated data.
- **Registration hygiene:** all classes registered/unregistered symmetrically, scene pointer removed, timers self-terminate, no handlers/draw-callbacks/msgbus left behind. All `poll()`s None-safe; `draw()`s cheap.
- **"Add Capture Cameras" removal is cleanly disconnected** (not registered, not referenced; files inert as intended).
- **No `sys.path` manipulation in Blender-side code** (the one hit runs only in the external conda interpreter — worth a clarifying comment for Extensions review, see L10). Manifest: AGPL-3.0 family license, `blender_version_min = 5.0.0`, `wheels = []` all correct for the headless architecture.
- **Rotation math + writer dimension swap correct; no preview/record orientation divergence on any live path** (calibration and takes load the same rotations file).
- **Subprocess hygiene:** list-form argv everywhere, no `shell=True`, spaces-in-paths safe; the processing runner drains a merged pipe on a reader thread and checks exit codes; sentinel writes are atomic.
- **`enforce_rigid_bodies` math is self-consistent** (deltas from original positions + cascade-to-descendants compose correctly; all 63 head/tail pairs verified against the hierarchy). Per-frame NaN/zero-length skips correct.
- **Spawn Rig re-run on the same take is leak-free** (`_purge_existing` handles objects, actions, armature data).
- **T-pose magic numbers** internally consistent and labeled verbatim-from-ajc27, per the 1:1 rule.
- **Memory correction:** the done-detection sentinel fix (open-bug memory `project_hiho_mocap_done_detection_bug`) **is implemented and shipping** — `is_done` checks the DONE/ERROR sentinels. What remains of that bug family is S2 (cancel defeats the sentinel writer) and M1 (stale-sentinel race).
