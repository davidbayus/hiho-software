**Date:** 2026-08-04 · **Build:** 1.4.32 · **Machine:** laptop (dev lead)
**Purpose:** harden the addon before the fall semester and the first recorded end-to-end
workflow demo.
**Method:** three independent read-only passes — capture/processing pipeline, Blender-side

Known and already-queued items were deliberately excluded so this report is all new

## Headline

**The pipeline is in good shape.** No crashes, no data loss, no corruption on the golden
path. Every serious finding from the 2026-06-09 audit is verifiably fixed in the current
source, and the code is clean on all three Blender 5.2 hazards on record (slotted actions,
geometry-nodes sockets, pose-matrix scale). That is a real result and worth saying plainly.

**But one bug outranks everything else in this report**, and it was found through the
separate jitter investigation rather than the audit sweep:

> **Every take where the performer turns around more than halfway is guaranteed to break
> under smoothing — and the addon manufactures the problem itself, at
> `operators/bake_animation.py:59`.**

Full diagnosis in `Z_JITTER_DIAGNOSIS_2026-08-04.md`. It is fix #1 below, and it is the
one thing that could visibly ruin a recorded demo.

The rest sorts into a short list of real bugs off the golden path, and a longer list of
cheap wins.

**Added same day, after the research sweep — a second HIGH data-quality finding:**

> **Every take is pre-filtered at the wrong frame rate.** FreeMoCap low-pass filters the
> 3D landmark positions before HIHO ever sees them, and that filter is told the footage
> is 30 fps while ours is 60. Verified on the live path:
> [process_take.py:158](external/process_take.py) builds the parameter model with pure
> defaults → the conda env's freemocap 1.8.2 defaults `framerate = 30.0`
> (`post_processing_parameter_models.py:32`) → the filter consumes exactly that value
> (`post_process_skeleton.py:50`) → nothing ever overwrites it. Effective result: the
> intended 7 Hz cleanup actually cuts around **14 Hz — half the designed smoothing —
> letting through exactly the 8–14 Hz band where hand jitter lives.** Every take David
> has hand-cleaned in Blender has been compensating for this. **Fix: one line in our own
> `process_take.py`** (set the model's framerate, and the sibling
> `butterworth_filter_parameters.sampling_rate`, from the take's real fps). All
> smoothing numbers measured today get re-derived after this lands.

## Fix these before the demo

### 1. The bake creates the smoothing jitter — CRITICAL
`operators/bake_animation.py:59`

Assigning `matrix_basis` per frame makes Blender re-derive the rotation from scratch, and
that always returns the "positive" spelling of the quaternion. Each frame is decided on its
own with no memory of the one before it, so whenever a bone turns past 180° the spelling
flips. The pose is identical either side — invisible — until smoothing averages across the
flip and the root swings the whole rig.

Measured on the 08-01 perimeter walk: **78.7° of error at the flip frames, against 0.98°
everywhere else.** Seven flips, matching seven crossings of the turn boundary.

**Fix:** run a continuity pass over the newly written curves at the end of the bake. The
code is already written and validated:
`HIHO_TESTING&CALIBRATION_BLENDS/HIHO_quaternion_continuity_repair.py`. It is provably
pose-neutral — across 13 bones and every third frame of the take, the resulting rotation
matrices differ by exactly zero. Design-doc-first per the standing rule.

### 2. Recording with an empty Cameras box silently records the wrong four cameras — HIGH
`operators/external_capture.py:181`, `properties.py:106`, `HIHO_Record.command:4,13`

The default is still `"0,1,2,3"` from the four-camera era, in three places. On the
six-camera ring, a blank box records four cameras — possibly including the laptop's
built-in — and the take looks normal until processing produces a worse solve than it
should. The `.command` launcher is worse: it is hardcoded to four cameras and 15 seconds.

**Fix:** make blank an error ("Click Show Cameras first") rather than a silent fallback,
and bring the launcher's camera list and duration in line with the ring.

### 3. Stopping a recording from the panel corrupts the take — HIGH
`operators/external_capture.py:117-121`, `core/external_runner.py:298-309`

The X button next to Record sends a kill signal that the recorder has no handler for, so
the video files are never finalized and end up unreadable. The folder still looks like a
real take. Days later it gets picked in the Take picker and Process fails minutes in with
an error from deep inside FreeMoCap.

Note the asymmetry: **ESC inside the window stops cleanly; the panel's Stop does not.** Two
stop buttons, opposite outcomes.

**Fix:** handle the signal in `external/record_take.py` and route it to the existing clean
stop, or mark the folder `_CANCELLED`.

### 4. Bake deletes every constraint on the rig, not just ours — MEDIUM (data loss)
`operators/bake_animation.py:51-54`

The loop removes all constraints unconditionally, even though `clear_hiho_constraints()`
and the `HIHO_` naming convention already exist for exactly this
(`core/bind_to_rig.py:150-154`).

Harmless on the skelly and on auto-rigged characters, where every constraint is ours. But
on a character with its own rigging — a downloaded rig, a student's IK setup, or the queued
CloudRig work — one click destroys the whole setup, and the report just says "N constraints
removed." Undo recovers it; saving afterward makes it permanent.

**Fix:** filter on the `HIHO_` prefix. Same blind spot inverted in `operators/save_out.py:32`,
which treats any constraint as "not baked yet."

## Real bugs, off the golden path

### 5. Crash text is thrown away — MEDIUM
`core/external_runner.py:311-353`

When a helper script crashes, its error message goes into a pipe that only the addon reads,
and the addon keeps nothing but its own status markers. David sees "backend exited with
code 1" and there is nothing in the system console either, because the console never got
it. Every future mystery failure is a dead end.

**Fix:** keep the last ~20 lines and attach them to the error. This is the cheapest
insurance in the whole report.

### 6. Moved takes can't be re-processed — MEDIUM
`external/process_take.py:92-108`, `external/calibrate.py:102-118`

Processing leaves absolute-path links inside the take folder. The documented workflow is to
shuttle takes into `HIHO_TESTING&CALIBRATION_BLENDS/` after capture — which breaks those
links for any take already processed once. Re-processing with a better calibration, a
routine move, then fails deep inside FreeMoCap. iCloud offloading breaks it the same way.

**Fix:** use relative links, and re-link any that no longer resolve.

### 7. Face take silently desyncs if the frame rate changes — MEDIUM
`core/face_take.py:239-241` vs `core/scene_clock.py:38-40`

Face keys are placed using whatever frame rate the scene has at load time. Loading a body
take afterward rewrites the scene frame rate from the take's sidecar. Load the face first
at 24 fps, then a 60 fps body take, and the face plays roughly two and a half times too
fast. Line Up Face matches the flash instant, so it looks aligned and then drifts. No
message anywhere.

**Fix:** warn loudly when the frame rate changes with a face take loaded, or rescale the
keys.

### 8. A failed Process leaves the previous take's green badge on screen — LOW
`operators/process.py:49-56`

The error branch sets the status line but never clears `process_verdict`. So the panel
reads "Processing failed" with an unnamed "Quality: GOOD" sitting directly beneath it. The
calibration badges were specifically hardened against this in July; the process badge was
not.

**Fix:** clear the verdict when Process starts, and put the take name on the badge like the
calibration badges already do.

### 9. Assorted smaller items
- **Map the Volume repeats the known silent-scorer bug** in a file written *after* that
  audit — `operators/volume_map.py:59,78` discards the crash text and then says "see system
  console," where nothing was printed.
- **Pointing the env preference at a folder gives a raw traceback** instead of the friendly
  message that already exists (`operators/external_capture.py:43` — `exists` should be
  `isfile`).
- **Process doesn't check the folder contains videos**, though Solve does — picking the
  wrong folder fails minutes later in FreeMoCap's language instead of immediately in ours.
- **Re-spawning after a bake leaks the baked action** each time
  (`operators/spawn_rig.py:114-131`).
- **Load Take turns Spawn Rig's friendly errors into traceback popups**
  (`operators/load_take.py:72-79`).
- **One undecodable byte in helper output kills the watcher thread**, leaving Record greyed
  out (`core/external_runner.py:270-277` — add `errors="replace"`).
- **A totally failed take reads "Quality: BAD (nanpx)"** instead of "no usable tracking in
  this take" (`external/process_take.py:74-89`).

## Packaging and demo readiness

- **The addon has never been committed to git.** Zero HIHO_MOCAP files are tracked; the
  last commit is from April. The entire May-to-July arc exists only as working files plus
  zips, replicated by iCloud alone. **One commit session is the cheapest insurance in this
  report.**
- **No license text ships anywhere.** AGPL-3.0 is correctly declared in the manifest, but
  there is no LICENSE file in the repo or the zip, and the vendored FreeMoCap carries no
  upstream license file. A compliance gap beneath this project's own philosophy.
- **`HIHO_Record.command` prints "Done. Saved to:" even when the recording failed**, and
  updates the last-capture pointer regardless. Exit code never checked.
- **The STATUS.md inside the 1.4.32 zip says the canonical build is 1.4.31** and unverified
  — a self-misidentifying install. It was the only file differing between the zip and the
  source tree; everything else is byte-identical.
- **There is no build script.** The zips are assembled by hand and their contents do not
  match the manifest's own rules, so "fresh zip each change" rests on memory. This also
  pre-breaks the queued Extensions-format install, which would produce a different file
  set.
- **The vendor-patch note describes a retired architecture.** The live FreeMoCap is the
  external conda env (1.8.2) and needs no patch; the `vendor/` tree is unpatched and has
  its GUI folder stripped, so re-engaging it would fail immediately. A future session
  following the old note would patch the wrong thing.
- **README.md is still the May "PPParty — under construction" page.**
- Ampersand check requested for the folder repointing: **both `.command` files are safely
  quoted throughout, and the Python side passes arguments as lists everywhere.** The `&` in
  `HIHO_TESTING&CALIBRATION_BLENDS` is harmless — as long as the repoint edit keeps the
  quotes.

Worth recording, because clean areas are information too:

- **Blender 5.2 compliance is complete.** All four keyframe writers use the slotted-action
  recipe correctly, matching Blender's own `anim_utils.py` byte for byte. No geometry-nodes
  socket access anywhere. The pose-matrix scale bug has no live trigger — the bake uses the
  canonical visual-bake recipe and no constraint introduces scale.
